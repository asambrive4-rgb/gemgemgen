### ~~1. 접근성 서비스 패키지 필터(`setServiceInfo`) 매 단계 동적 재설정 IPC 제거~~ (완료)
- **관련 파일**: [`GeminiAccessibilityService.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/automation/android/GeminiAccessibilityService.kt)

#### ⚙️ 실제 앱 내부 동작 메커니즘
- GemGemGen의 자동화 엔진은 접근성 이벤트 수신 방식(`onAccessibilityEvent`)이 아니라, 필요할 때 타겟 앱(Gemini, ChatGPT 등)의 윈도우 노드 트리를 직접 폴링/탐색하는 방식으로 작동합니다.
- 이미 `AccessibilityNodeTraversal` 내부에서 노드를 조회할 때 `targetPackages`에 지정된 패키지(예: `com.google.android.googlequicksearchbox`)가 맞는지 자체 필터링을 완벽하게 수행하고 있습니다.
- 그런데 현재 코드는 세부 동작 하나하나마다 안드로이드 OS(`system_server`)에 `setServiceInfo` 시스템 콜을 날립니다:
  1. 새 채팅 버튼을 누르기 전: `setServiceInfo`로 Gemini 패키지만 구독 등록 (OS와 Binder IPC 발생)
  2. 클릭 직후: `setServiceInfo`로 구독 해제 (`null` 전달, Binder IPC 발생)
  3. 프롬프트 입력창을 찾기 전: 다시 `setServiceInfo` 등록 (Binder IPC 발생)
  4. 텍스트 입력 후: 다시 구독 해제 (Binder IPC 발생)
  5. 전송 버튼 클릭 전: 다시 등록 (Binder IPC 발생)...
- 이로 인해 프롬프트 1개를 전송하는 짧은 시간 동안 **앱 프로세스와 안드로이드 시스템 프로세스 사이에 무거운 Binder IPC 통신이 8~10회나 왕복**합니다.

#### ⚠️ 야기하는 문제
- 안드로이드의 Binder IPC는 프로세스 경계를 넘는 시스템 호출(System Call)이므로 CPU 컨텍스트 스위칭과 데이터 직렬화 비용이 발생합니다.
- 매 스텝마다 OS와 동기화하느라 자동화 파이프라인에 미세한 병목(Stuttering)이 누적됩니다.
- 이를 관리하기 위해 `BasePackageScopedAutomation`, `applyAccessibilitySubscription` 등 불필요한 래퍼 계층 약 115줄이 아키텍처를 복잡하게 만듭니다.

#### ✨ 수정 후 앱 동작 및 UX 변화
- 자체 노드 탐색기가 이미 패키지를 철저히 검사하므로, OS에 매번 구독을 넣었다 뺐다 하는 과정을 완전히 제거합니다.
- **겉으로 보이는 자동화 순서는 그대로 유지**되면서, 내부적으로 시스템 통신 오버헤드가 제로가 되어 **스텝 간 전환이 끊김 없이 매끄럽게 이어집니다.**

### 2. 프롬프트 입력·전송 시 무조건적인 고정 500ms 대기 및 중복 트리 탐색 축소
- **관련 파일**: [`AccessibilityPromptAutomation.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/automation/android/AccessibilityPromptAutomation.kt#L145-L180) (및 L247–L331)

#### ⚙️ 실제 앱 내부 동작 메커니즘
- `applyPromptText()` 메서드는 입력창을 클릭하고 150ms 후 `ACTION_SET_TEXT`로 프롬프트를 주입한 뒤, `targetNode.refresh()`를 거쳐 `isNodeTextApplied()`로 **텍스트가 타겟 앱에 정상 반영되었는지 이미 확실하게 검증하고 `true`를 반환**합니다.
- 그러나 상위 호출부인 `setPromptText()`에서는 이미 성공했음에도 불구하고:
  ```kotlin
  // 검증이 끝났는데도 무조건 500ms 동안 코루틴을 재움
  delay(500L)
  // 그리고 접근성 루트 노드부터 화면 전체 트리를 다시 재귀 탐색함
  if (!isPromptTextApplied(...)) { ... }
  ```
- 여기에 더해 전송 버튼을 누르는 `clickSendWhenReady()`에서도 클릭 직후 무조건 `delay(500L)`를 쉬고, 버튼 상태 확인 실패 시 루프 안에서 또 `delay(500L)`를 대기합니다.

#### ⚠️ 야기하는 문제
- 스마트폰 하드웨어가 아무리 빠르고 타겟 앱이 즉시 반응하더라도, 코드에 박혀 있는 고정 `delay(500L)` 때문에 **프롬프트 1회 전송마다 최소 0.6초~1.0초의 순수 대기 시간이 강제로 낭비**됩니다.
- 10개의 프롬프트를 연속 변주 전송하는 시나리오라면, 아무것도 안 하고 멍하니 잠자는 시간만 **6초에서 10초 이상 누적**됩니다.

#### ✨ 수정 후 앱 동작 및 UX 변화
- 이미 텍스트 입력과 반영이 확인되었다면 500ms 고정 대기를 즉시 통과시키고, 전송 버튼 대기도 조건 만족 시 즉시 탈출하는 짧은 폴링(50ms 단위)으로 통합합니다.
- **사용자 UX 관점에서 자동화 전송 속도가 눈에 띄게 빨라집니다.** 프롬프트가 입력창에 들어가자마자 찰나의 지체도 없이 전송 버튼이 딱딱 눌리는 쾌속 전송을 경험할 수 있습니다.

### 3. 키보드 개폐 애니메이션 중 60~120fps 전체 화면 리컴포지션 및 IME 이중 여백 점프 제거
- **관련 파일**: [`MainTabbedScreen.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/ui/MainTabbedScreen.kt#L69), [`AutomationScreen.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/automation/ui/AutomationScreen.kt#L55), [`AnalysisScreen.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/analysis/ui/AnalysisScreen.kt#L92-L98)

#### ⚙️ 실제 앱 내부 동작 메커니즘
1. **키보드 인셋 매 프레임 읽기**:
   - `val isImeVisible = WindowInsets.ime.getBottom(LocalDensity.current) > 0` 구문이 `derivedStateOf` 없이 최상위 컴포저블 본문에서 직접 호출되고 있습니다.
   - 가상 키보드가 올라오거나 내려가는 약 300ms 동안 바닥 픽셀 높이는 `0 -> 25 -> 80 -> ... -> 850px`로 매 프레임 연속해서 변합니다.
   - Compose 런타임은 관찰 중인 State가 변했다고 판단하여, 120Hz 고주사율 디스플레이 기준 **300ms 동안 화면 전체를 초당 60~120번 연속으로 Recomposition(재계산 및 재렌더링)**합니다.
2. **`AnalysisScreen`의 이중 IME 여백 가산**:
   - 화면 루트 `Box`에 이미 `.imePadding()`이 붙어 있어 시스템이 키보드 높이만큼 화면을 밀어 올려줍니다.
   - 그런데 하단의 `AnalysisBottomSpacer`에서 `if (isImeVisible) 260.dp else 160.dp`로 100dp의 여백을 한 번 더 더해줍니다.

#### ⚠️ 야기하는 문제
- 텍스트 입력창을 터치해 키보드가 열리는 순간 극심한 프레임 드랍(Jank)이 발생해 화면이 뚝뚝 끊깁니다.
- `AnalysisScreen`에서는 키보드가 다 올라온 순간 100dp 여백이 추가로 팽창하면서 화면 전체 내용이 위로 **쿵! 하고 튕겨 올라가는 부자연스러운 시각적 점프**가 발생합니다.

#### ✨ 수정 후 앱 동작 및 UX 변화
- `remember { derivedStateOf { WindowInsets.ime.getBottom(...) > 0 } }`로 감싸면, 키보드 높이 숫자가 아무리 춤을 춰도 결과 불리언 값(`false` -> `true`)이 뒤집히는 **단 1회만 Recomposition이 발생**합니다.
- 키보드가 올라오고 내려갈 때 120fps 주사율이 온전히 유지되어 **쫀득하고 부드러운 키보드 전환 애니메이션**이 구현됩니다.
- 바닥 여백 이중 가산을 제거하여 키보드가 올라와도 **입력창과 버튼들이 안정적인 위치에 얌전히 안착**합니다.

### 4. 분석 프롬프트(`AnalysisPromptBuilder`)의 Kotlin `.toString()` 날것 전송 및 중복 문구 제거
- **관련 파일**: [`AnalysisPromptBuilder.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/analysis/domain/AnalysisPromptBuilder.kt#L133-L173)

#### ⚙️ 실제 앱 내부 동작 메커니즘
- 프롬프트 정밀 분석 및 2단계 변주 생성 시 LLM(Gemini/Grok)에게 보낼 프롬프트 텍스트를 구성할 때, 개발용 Kotlin 데이터 클래스 인스턴스들을 포맷팅 없이 문자열 템플릿에 그대로 넣고 있습니다:
  ```kotlin
  // 실제 주입되는 문자열:
  // "editableRanges: [AnalysisSourceRange(startIndex=12, endIndex=45, tag=null)]"
  "${targetSegment.editableRanges}"
  "${analysisReport.targetVisualContext}"
  "${analysisReport.cascadingTrace}"
  ```
- 심지어 상단 지시문에서는 *"do not calculate start/end character indices(시작/끝 글자 인덱스는 계산하지 마라)"*라고 명령해 놓고, 바로 아랫줄에 기계 인덱스 덤프를 전송하고 있습니다. 또한 `$variationGoal` 변수도 두 번 중복 결합됩니다.

#### ⚠️ 야기하는 문제
- 무의미한 기계 객체 덤프로 인해 LLM API에 불필요한 **입력 토큰(Input Tokens)이 낭비**됩니다.
- 입력 토큰이 커지면 LLM 서버의 첫 토큰 생성 시간(Time to First Token)이 지연됩니다.
- LLM의 주의력(Attention)이 쓸모없는 인덱스 숫자에 분산되어, 모델이 지시사항을 오해하거나 변주 결과물의 품질이 떨어지는 원인이 됩니다.

#### ✨ 수정 후 앱 동작 및 UX 변화
- 기계 클래스 덤프를 걷어내고 실제 변경할 대상 텍스트 영역만 깔끔하게 정제해서 전송합니다.
- **LLM의 응답 생성 속도가 단축**되고, 프롬프트의 지시 맥락이 명확해져 **변주 텍스트의 자연스러움과 퀄리티가 향상**됩니다.

### 5. Grok 세션 인메모리 캐시 도입 및 불필요한 매회 Billing 쿼터·Discovery 조회 정리

#### ✨ 수정 후 앱 동작 및 UX 변화
- **사용자가 보는 화면과 동작 기능은 100% 동일하게 유지**됩니다.
- 내부적으로 ViewModel은 인증/프롬프트 엔진 등의 독립 위임자(Delegate)로 분리되고, UI 컴포넌트도 서브 파일로 명확히 쪼개집니다.
- **리컴포지션 범위가 하위 컴포넌트 단위로 격리되어 렌더링 효율이 상승**하고, 앞으로 바이브코딩으로 기능을 추가하거나 수정할 때 **버그 발생 가능성이 획기적으로 낮아집니다.**
