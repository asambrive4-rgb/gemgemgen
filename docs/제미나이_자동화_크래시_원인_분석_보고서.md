# 제미나이 자동화 스트레스 테스트 및 앱 크래시 원인 분석 보고서

## 1. 개요

* **문서 목적**: 대량 프롬프트 주입 자동화 환경에서 발생하는 제미나이(Gemini) 앱 비정상 종료(Crash)의 정량적 데이터, 시스템 이벤트 및 발생 메커니즘을 상세히 기록하여 후속 에이전트 및 개발자가 시스템 설계에 활용할 수 있도록 함.
* **테스트 일시**: 
  * 1차 실험 (144회): 2026-10-03 17:55:55 ~ 18:06:47
  * 2차 실험 (200회): 2026-10-03 18:13:41 ~ 18:26:47
  * **총 누적 생성 회차**: **344회**
* **테스트 대상**:
  * 대상 AI 앱: Google Gemini (런처 스텁: `com.google.android.apps.bard`, 실제 런타임 호스트: `com.google.android.googlequicksearchbox:search`)
  * 자동화 제어 앱: GemGemGen (`com.example.gemgemgen`)
* **테스트 환경**: Android 무선 디버깅 (ADB over TCP/IP, 기기 포트: `192.168.137.204:40545`)

---

## 2. 실험 환경 및 방법

### 2.1. 테스트 파라미터 및 규모
* **1차 실험**: 1세션당 12회 생성 × 12개 세션 = 총 144회
* **2차 실험**: 1세션당 20회 생성 × 10개 세션 = 총 200회
* **프롬프트 특성**: 시스템 지침(System Instruction) 및 이미지 생성 프롬프트 포함 텍스트 (길이 약 1,500자)
* **제어 방식**: GemGemGen UI 시작 버튼(`X=144, Y=1640`) 자동 탭 주입 및 접근성 서비스(`GeminiAccessibilityService`) 연동

### 2.2. 로깅 및 모니터링 체계
* **로그캣(Logcat) 실시간 수집**:
  * `logcat -v threadtime`: 전체 시스템 런타임 로그 실시간 파일 캡처 (`logcat_full.txt`)
  * `logcat -b events -v threadtime`: 안드로이드 OS 프로세스 생명주기 및 충돌 이벤트 캡처 (`logcat_events.txt`)
* **메모리 및 프로세스 추적**:
  * `dumpsys meminfo com.google.android.googlequicksearchbox:search`: 실제 런타임 프로세스 PSS(Proportional Set Size) 실시간 기록
  * `dumpsys window displays`: 포그라운드 윈도우 포커스 추적 (`mCurrentFocus`)
  * 프로세스 생명주기 트랩: `am_crash`, `am_proc_died`, `am_kill`, `lowmemorykiller`

## 4. 앱 크래시 원인 상세 분석

### 4.1. 제1원인: `android.os.TransactionTooLargeException` (압도적 핵심 원인)

#### (1) 실측 시스템 이벤트 로그 (2차 실험 크래시 타임라인)

#### (2) Logcat 번들 상세 구조

#### (3) 메커니즘 분석
1. **바인더 IPC 제한**: 안드로이드 OS의 IPC Binder 단일 트랜잭션 한도는 약 **500KB**임.
2. **누적 한계점(Threshold)**: Google App의 `ActivityResultRegistry`에 `KEY_COMPONENT_ACTIVITY_REGISTERED_KEYS`가 해제 없이 계속 적체됨.
3. **정량적 폭발 시점**: 20회 생성 조건에서는 정확히 **2세션 누적(약 38~40회 생성)** 시점에 파셀 크기가 **522,916 bytes (~510KB)**에 도달하며 OS에 의해 프로세스가 즉사함.

### 4.2. 제2원인: `java.lang.OutOfMemoryError` 및 PSS 메모리 팽창

#### (1) 발생 증거 로그
```text
10-03 17:58:04.917  1356  4800 I am_crash: [12577,0,com.google.android.googlequicksearchbox:search,-1529102651,java.lang.OutOfMemoryError,Failed to allocate a 40 byte allocation with 5232560 free bytes and 5109KB until OOM, target footprint 536870912, growth limit 536870912; giving up on allocation because <1% of heap free after GC.,PG,28,0]
```

#### (2) 메모리 추이 분석
* **JVM 힙 고갈**: 64비트 안드로이드 시스템 JVM 힙 상한선인 **512MB (`536,870,912 bytes`)**에 도달 시 단 40바이트 추가 할당도 불가능하여 OOM 발생.
* **PSS 메모리 팽창**: 2차 실험 세션 5에서 프로세스 전체 PSS 메모리가 **1,026,873 KB (약 1.02GB)**까지 치솟으며 시스템 리소스를 심각하게 점유함.

## 5. 아키텍처 관측 사실

1. **프로세스 이원화**:
   * 제어 대상 패키지: `com.google.android.apps.bard` (런처 스텁)
   * 실제 런타임 호스트 프로세스: `com.google.android.googlequicksearchbox:search` (실제 대화 렌더링, 웹뷰, 힙/바인더 메모리 점유 주체)
2. **재현 주기성 (Deterministic Reproducibility)**:
   * 12회 단위 실행: 약 36~48회 주기 크래시
   * 20회 단위 실행: 약 38~40회 주기 크래시
   * **관측 결론: 1회 실행 단위와 무관하게 누적 생성 횟수가 약 35~40회에 도달하면 바인더 트랜잭션 버퍼(500KB)가 초과되어 예외 없이 프로세스 크래시가 발생함.**
