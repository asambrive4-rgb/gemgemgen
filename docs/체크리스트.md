### 2. 프롬프트 입력·전송 시 무조건적인 고정 500ms 대기 및 중복 트리 탐색 축소
- **관련 파일**:
  - [`AccessibilityPromptAutomation.kt`](file:///c:/Users/joajo/AndroidStudioProjects/gemgemgen/app/src/main/java/com/example/gemgemgen/automation/android/AccessibilityPromptAutomation.kt#L145-L180) (및 L247–L331 `applyPromptText`, `setPromptText`, `clickSendWhenReady`)
- **어떤 문제인가요?**:
  - `applyPromptText()` 내부(L153–L166)에서 이미 입력창 클릭 후 `150ms` 대기 → 텍스트 입력(`ACTION_SET_TEXT`) → `targetNode.refresh()` → `isNodeTextApplied(targetNode, prompt)`로 **텍스트가 제대로 들어갔는지 확인까지 마치고 `true`를 반환**합니다.
  - 그런데 이를 호출한 `setPromptText()`(L266–L275)에서 성공 여부와 상관없이 **무조건 `delay(500L)`를 또 기다린 뒤** 접근성 트리를 처음부터 다시 뒤져(`isPromptTextApplied`) 재확인합니다.
  - 마찬가지로 `clickSendWhenReady()`(L304–L327)에서도 전송 버튼 클릭 직후 무조건 `delay(500L)`를 기다리고, 실패 시 루프 안에서 또 `delay(500L)`를 중복 대기합니다.
- **실제 영향**:
  - 텍스트가 즉시 입력되고 전송이 즉시 완료되는 정상 상황에서도 매 프롬프트마다 최소 0.6~1.0초씩 허공에 대기 시간이 소모됩니다(10회 반복 시 6~10초 지연).
- **개선 방안**:
  - `applyPromptText()`가 이미 반영 확인까지 성공했다면 추가 500ms 블로킹 대기를 건너뛰거나 짧은 폴링으로 즉시 통과시키고, `clickSendWhenReady()`의 중복 대기를 단일 폴링 루프로 통합합니다.

  2. 앱 시작 시, 프로바이더 변경 시, 그리고 **매번 생성이 끝날 때마다** 외부 프록시(`cli-chat-proxy.grok.com/v1/billing`)에 추가 HTTP 요청을 보내 화면 전체 리컴포지션을 유발하며, 로그인 시에도 고정된 xAI OAuth 엔드포인트를 매번 `.well-known/openid-configuration`에서 동적 조회합니다.
- **개선 방안**:
  - `AndroidEncryptedGrokAuthRepository`에 인메모리 세션 캐시를 추가(복호화 3회 → 0~1회)하고, 불필요한 Billing 쿼터 조회 계층(`GrokBillingGateway` 등) 및 OAuth Discovery 동적 조회를 상수/선택적 조회로 경량화합니다.
